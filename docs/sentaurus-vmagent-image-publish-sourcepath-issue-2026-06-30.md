## Summary

When the browser user asks the VM agent to send the zoomed gate image, the chat only shows a short text reply. The image is not shown in the chat bubble.

Current evidence shows this is not a frontend rendering failure. The backend message API does not contain an image attachment for the failed replies. Instead, the VM worker records an attachment publish failure:

```text
Progress: attachment_publish failed - Failed to publish image: sourcePath does not exist
```

The VM worker appears to consume the `<VM_SESSION_FILE>...</VM_SESSION_FILE>` block, remove it from visible text, fail to publish the file because `sourcePath` does not exist, then still append the remaining text as a normal agent message with `attachments: null`.

Result: the user sees only text, with no clear explanation in the normal chat bubble that image publishing failed.

## User-Visible Symptom

The user asks for the enlarged gate image in the frontend chat.

Observed final chat output was equivalent to:

```text
I am directly re-publishing the gate local zoom image generated by the previous `svisual -batchx` run. This time I will send only the image publish block to avoid extra text.
```

No image appears after this text.

## Why This Is Not Primarily a Frontend Bug

The frontend chat renderer already displays image attachments when they exist.

Relevant frontend behavior in `apps/web/src/App.tsx`:

- `visibleMessages` filters out only progress and thinking messages.
- Normal `agent` messages are shown.
- `message.attachments` are rendered under the message bubble.
- `kind: "image"` attachments are rendered with image preview cards.

Therefore, if the backend returned:

```json
{
  "attachments": [
    {
      "kind": "image",
      "source": "vm-session-file",
      "path": "some_image.png",
      "contentType": "image/png"
    }
  ]
}
```

the frontend should display it.

The failed message has `attachments: null`, so there is nothing for the frontend to preview.

## Current VM Worker Flow

Relevant host-side embedded VM worker source:

```text
apps/server/src/services/vmAgent.ts
```

Important functions/locations:

```text
extract_vm_session_files(reply)
publish_vm_session_file(session_id, spec)
process_queue_file(...)
```

Current flow:

1. LLM returns a visible reply that may include `<VM_SESSION_FILE>...</VM_SESSION_FILE>`.
2. `extract_vm_session_files(reply)` extracts those blocks.
3. The extracted blocks are removed from visible reply text.
4. Worker calls `publish_vm_session_file(session_id, spec)`.
5. `publish_vm_session_file` requires a real image path under `~/STDB`.
6. If `sourcePath` does not exist, it raises:

```text
sourcePath does not exist
```

7. Worker records a progress failure:

```text
attachment_publish failed
```

8. Worker still appends the remaining visible text as the final agent message.
9. Since publish failed, no `display_attachments` entry is attached to the final message.

## Root Cause

The VM agent relies on the LLM to provide a correct absolute `sourcePath` in a `VM_SESSION_FILE` block.

For the gate zoom image case, the LLM likely guessed or reused a stale path. The generated path did not exist on the VM filesystem, so the publish step failed.

The publish block is then removed from the final visible text, and the user sees only a generic text reply. The actual publish failure is visible only as a progress event, which is easy to miss.

This is a VM agent protocol and error-surfacing issue.

## Required Fix

### 1. Stop asking the LLM to guess absolute sourcePath

The current protocol:

```xml
<VM_SESSION_FILE>{
  "category": "simulation image",
  "name": "gate_zoom.png",
  "sourcePath": "/home/TCAD2022/STDB/.../gate_zoom.png"
}</VM_SESSION_FILE>
```

is fragile because the LLM can invent or stale-copy `sourcePath`.

Prefer a manifest-based protocol:

```xml
<VM_SESSION_FILE>{
  "category": "simulation image",
  "name": "gate_zoom.png",
  "runId": "run_20260629T140105Z_svisual-smoke-gate-zoom_556a69",
  "artifactPath": "gate_zoom.png"
}</VM_SESSION_FILE>
```

The worker should resolve `runId + artifactPath` against the known safe run directory:

```text
~/STDB/web-agent-runs/<runId>/<artifactPath>
```

This keeps the model from fabricating absolute paths while preserving the existing safety boundary.

### 2. Add source resolution fallback

`publish_vm_session_file(session_id, spec)` should support, in order:

1. `runId + artifactPath`
2. existing `sourcePath` or `path`, but only if it is under safe VM directories
3. existing session output file reference, if `category + path` is provided

Allowed source roots should remain restricted:

```text
~/STDB/web-agent-runs
~/STDB/web-agent-sessions
~/.sentaurus-web-agent/vm-agent/generated
```

Do not add arbitrary shell execution or arbitrary file read endpoints.

### 3. Surface publish failures in the final chat message

If all publish attempts fail, the final agent message must not silently become a normal text-only reply.

Append a visible failure notice to the final chat content, for example:

```text
Image publish failed: sourcePath does not exist. No chat image attachment was created.
```

Also include structured metadata:

```json
{
  "vmSessionFilePublishErrorsJson": "[{\"name\":\"gate_zoom.png\",\"error\":\"sourcePath does not exist\"}]"
}
```

This lets the frontend show a clear error chip later.

### 4. Preserve failed publish diagnostics

When `publish_vm_session_file` fails, include enough data in audit logs and message metadata to debug:

```json
{
  "sessionId": "run_20260626163724_rDsE4Q",
  "name": "gate_zoom.png",
  "category": "simulation image",
  "runId": "run_...",
  "artifactPath": "gate_zoom.png",
  "sourcePath": "...",
  "error": "sourcePath does not exist"
}
```

Avoid exposing secrets or arbitrary host paths to the browser.

### 5. Prefer automatic artifact attachments for Sentaurus runs

When a run produces image artifacts such as `.png`, `.jpg`, `.jpeg`, `.webp`, or `.gif`, the final `sentaurus_run` message should automatically include them as:

```json
{
  "source": "vm-run-artifact",
  "kind": "image",
  "runId": "<runId>",
  "path": "<artifactPath>",
  "name": "<basename>",
  "contentType": "image/png"
}
```

This already appears partially implemented through `display_attachments_for_artifacts(...)`; verify it includes the gate zoom run artifacts and that the artifact list actually contains the PNG path.

## Acceptance Criteria

1. Asking the VM agent to show the previously generated gate zoom image results in a chat message with an image preview.
2. The final backend message contains a non-empty `attachments` array with `kind: "image"`.
3. The image attachment uses either:
   - `source: "vm-run-artifact"` with `runId + path`, or
   - `source: "vm-session-file"` with `runId + category + path`.
4. If the source image cannot be found, the normal chat bubble clearly says image publishing failed.
5. The worker no longer relies only on LLM-guessed absolute `sourcePath` for existing run artifacts.
6. Invalid paths outside allowed VM roots are still rejected.
7. No raw shell endpoint or arbitrary file read is introduced.

```xml
<VM_SESSION_FILE>{"category":"simulation image","name":"gate_zoom.png","sourcePath":"/home/TCAD2022/STDB/missing/gate_zoom.png"}</VM_SESSION_FILE>
```

Expected:

- Worker rejects it.
- Final message visibly reports image publish failure.
- `attachments` is empty or omitted.
- Structured publish error metadata exists.

### Test C: unsafe sourcePath

Input publish block:

```xml
<VM_SESSION_FILE>{"category":"simulation image","name":"x.png","sourcePath":"/etc/passwd"}</VM_SESSION_FILE>
```

Expected:

- Worker rejects it.
- No file is copied.
- No attachment is created.
- Error says source path is outside allowed roots.

### Test D: run completion artifact attachment

Run a safe `svisual -batchx gate_zoom.tcl` request that generates a PNG.

Expected:

- Final `sentaurus_run` message includes PNG artifact attachment automatically.
- User does not need a second "send the image again" prompt.
